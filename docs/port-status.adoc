= Java Port Status
:toc:

Where the port of Asciidoctor (Ruby) to Java stands, as of 2026-10-13.

The port follows Asciidoctor Ruby at commit `52871a02` (main branch, 2026-10-11).

== Summary

* Gradle multi-project build: `asciidoctorj-api` (the AsciidoctorJ API, unchanged), `asciidoctorj-core` (`org.asciidoctor:asciidoctorj`), `asciidoctorj-cli`, `asciidoctorj-test-support`, `asciidoctorj-documentation`, `asciidoctorj-springboot-integration-test`; `options.release` 17, no runtime dependency.
* JDK: `export JAVA_HOME=~/.sdkman/candidates/java/25.0.4-tem` (not the default JDK).
* Build: `./gradlew --offline build`, a single test class: `./gradlew --offline :asciidoctorj-core:test --tests DocumentTest`, compile only: `./gradlew -q --offline testClasses`.
* CI: GitHub Actions (`.github/workflows/ci.yml`) on Linux, Windows and macOS.
* Size: ~29,000 lines (main), ~44,500 lines (test).
* Test suite: *2847 tests translated from Ruby* (2725 in `asciidoctorj-core`, 122 in `asciidoctorj-cli`) and *422 tests of AsciidoctorJ* (`asciidoctorj-core`, package `org.asciidoctor`; the Groovy tests are converted to Java, the tests that rely on JRuby are removed and the tests that rely on Ruby gems are disabled), 0 failures (all the skipped tests have an explicit `@Disabled` reason).

== Layout

* Flat package `org.asciidoctor.core`, one Java class per Ruby class (`Document`, `Parser`, `Reader`, `PreprocessorReader`, `Substitutors`, `AbstractNode`, `AbstractBlock`, `Block`, `Inline`, `List`, `ListItem`, `Section`, `Table` (+ `Table.Rows`, `Table.Row`, `Table.Column`, `Table.Cell`), `Rx`, `Helpers`, `Strings`, `PathResolver`, etc.). No `ast` subpackage (the AST of the AsciidoctorJ API is implemented by wrappers, see below).
* Subpackages: `converter`, `extension`, `syntaxhighlighter`, `log` (and `cli` in the `asciidoctorj-cli` module).
* Resources: `asciidoctorj-core/src/main/resources/org/asciidoctor/data/{stylesheets,locale}`; the CLI resources are in `asciidoctorj-cli/src/main/resources/org/asciidoctor` (`data/reference`, `man/asciidoctor.1`).
* Test fixtures: `asciidoctorj-core/src/test/resources/fixtures` (also used by the CLI tests).
* Migration guide: `docs/migration-from-asciidoctorj.adoc`.

== API choices

* The public API is the AsciidoctorJ API (`asciidoctorj-api`, imported unchanged), implemented in `org.asciidoctor.core.api` with adapters over the port (like the JRuby implementation over the Ruby objects), so that the port stays faithful to Ruby:
** `CoreAsciidoctor` implements `org.asciidoctor.Asciidoctor` (service, created by `Asciidoctor.Factory.create()`). Each instance holds its extensions, converters, syntax highlighters and log handlers and passes them to the port with the options of each conversion (`extension_registry`, `converter_factory`, `syntax_highlighter_factory`, `logger`), so the instances are isolated like the JRuby instances (one Ruby runtime each).
** `api.ast`: the nodes of the API wrap the nodes of the port; the wrapper is cached on the node (`AbstractNode#getApiNode`), so a node is always represented by the same instance.
** `api.extension`: `ProcessorImpl` (the delegate of `BaseProcessor`, created by `ProcessorFactoryImpl`, a service), the proxies of the processors (subclasses of the processors of the port), `JavaExtensionRegistryImpl`/`ExtensionGroupImpl`. The configuration and the annotations of the processors of the API are converted to the configuration of the port (a String that starts with a colon is a Ruby symbol).
** `api.converter`, `api.syntaxhighlighter`, `api.log`: the proxies of the converters and syntax highlighters, and the bridge between the logger of the port and the `LogHandler`s.
** For compatibility, the SPIs, the directory walkers and `AsciidoctorCoreException` of AsciidoctorJ are provided in `org.asciidoctor.jruby`.
* The port also has a static API (like Ruby/JS): `org.asciidoctor.core.Asciidoctor.load/loadFile/convert/convertFile`, with `Map<String,Object>` and `Options` overloads (used by the tests translated from Ruby). It also has AsciidoctorJ-like classes that predate the implementation of the API (`Options`/`Attributes` builders, extension annotations, `log.LogHandler`): they could be removed in favor of the API.
* Generic converters: `Converter<T>`, `AbstractConverter<T>`, `CompositeConverter<T>`, `Writer<T>`/`VoidWriter<T>`; `Asciidoctor.convert(input, options, Class<T>)`, `Document.convert(Class<T>)`, `Document.convertOutput(Map)`. A `byte[]` output is written as is; any other type requires the converter to implement `Writer` (otherwise `IllegalStateException`). Postprocessors only apply to `String` output.
* Logging: `Logger`/`LoggerManager`/`MemoryLogger`/`NullLogger` (Ruby). The `logger` option binds the logger to the current thread (a `ThreadLocal`, instead of replacing the global logger like Ruby does); the `Document` keeps it and binds it again on `parse`/`convert`. The CLI changes the global logger (`--verbose`/`--quiet`/`--log-level`), which is fine since it runs its conversions sequentially in a single process.
* CLI: `org.asciidoctor.cli.Invoker` (main class of the jar) and `cli.Options` (OptionParser clone), which convert the documents with the AsciidoctorJ API (an `Asciidoctor` instance per invocation, a `LogHandler` that writes the messages in the format of Asciidoctor and tracks the maximum severity for `--failure-level`); only `--timings` uses the implementation (`Timings`). `-r` loads a Java class (an `ExtensionRegistry`, registered with the instance), `-I` adds an entry to the class path.
* The questions about the API for the maintainers are in `docs/api-notes.adoc`.

== Test translation tooling

* `tools/rb2java.rb`: translates the Ruby AST to JUnit 5.
* `tools/fix_tests.py`: per-test fixes (replacements, disabling with a reason, body rewrites, extra members/imports).
* `tools/regen.sh Name...`: regenerates test classes (skips the ones containing "ported by hand", e.g., `LoggerTest`, `ConverterTest`).
* `tools/errors.sh` (compilation errors with source line), `tools/failures.sh` (lists surefire failures).
* `tools/compare/compare.sh <name> <dir>`: converts every AsciiDoc file of a corpus with Asciidoctor Ruby and with the Java port (HTML5), then diffs the HTML and the log messages (`ATTRS` adds attributes, `EXT` changes the file extension).
* `TestHelper.java` holds the equivalents of the Ruby test helpers (XPath/CSS, CLI, test web server, `Ref`, etc.).

== Upstream changes not ported

The upstream commits between `29837383` (initial port) and `52871a02` were ported one by one (see the Git history, each commit references the upstream issue). The following changes are specific to Ruby or Opal and were intentionally left out:

* `603582a1`, `a4f929bc`: Asciidoctor.js (Opal) workarounds.
* `94ec5e0b`, `0908d45f`, `6dd6cfbe`, `3c4e3ea6`: Rubocop and Ruby-only refactorings.
* `568c3835`, `593c4d1d`: Ruby `Logger` specifics (the tests of `593c4d1d` were ported to `LoggerTest`); `f79ad7ed`, `52871a02`: `File::NULL` logger test.
* `6d7f7275`: OpenURI require logic.
* `7175fc32`, `261529d0`: change reverted upstream.

Known upstream bug not reproduced: when the style of an ordered list is implied by the marker (e.g., `a.`), Asciidoctor Ruby stores the style as a Symbol and omits the `type` attribute on the `<ol>` element; the Java port always emits it.

== Known differences with AsciidoctorJ

* `BlockProcessor.process` returns `AbstractBlock` (AsciidoctorJ: `Object`).
* Log severity: `Logger.Severity` (not `org.asciidoctor.log.Severity`).
* Attribute names are typed `String` (not `Object`); `ContentModel` is an enum (not a `String`).
* `getParent()` returns `AbstractNode`.
* `Asciidoctor.convert(x, null)` is ambiguous (`Map` / `Options` overloads).

== Not supported

* Ruby extensions / `requireLibrary`.
* Tilt templates (`template_dirs`).
* Rouge, CodeRay and Pygments syntax highlighter adapters (the `SyntaxHighlighter` API remains extensible; highlight.js is ported).
* `convertDirectory` / `convertFiles`.
