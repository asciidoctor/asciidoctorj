= Contributing

== Commit messages

Commit messages follow the https://www.conventionalcommits.org/en/v1.0.0/[Conventional Commits] specification:

----
<type>[optional scope]: <description>

[optional body]

[optional footer(s)]
----

The description is written in the imperative mood, in lowercase, without a trailing period (e.g., `fix: escape the ampersand in link text`).

Types:

[horizontal]
`feat`:: a new feature (or an upstream feature ported from Asciidoctor)
`fix`:: a bug fix
`docs`:: documentation only
`test`:: adding or fixing tests (including the test translation tools)
`refactor`:: a code change that neither fixes a bug nor adds a feature
`perf`:: a performance improvement
`style`:: formatting, no change of behavior
`build`:: build system or dependencies (`*.gradle`, `gradle/libs.versions.toml`)
`ci`:: continuous integration (`.github/workflows`)
`chore`:: other changes (repository configuration, etc.)

The scope is optional and names the affected area, e.g., `converter`, `extension`, `cli`, `parser`, `logger`.
A breaking change is marked with `!` after the type or scope (e.g., `feat(api)!: ...`) and described in a `BREAKING CHANGE:` footer.

When a commit ports an upstream change, reference the Asciidoctor commit or issue in the body (e.g., `Port of asciidoctor/asciidoctor@29837383`).

== Releasing the native implementation

A release of the native implementation is made by running the *Native Release* workflow from the `main` branch (Actions > Native Release > Run workflow), with the version to release (e.g., `4.0.0`) and, optionally, the next development version (by default, the next patch version, e.g., `4.0.1-SNAPSHOT`, or the same version after a prerelease such as `4.0.0-rc.1`).

The workflow:

. sets the version (`nativeVersion`), builds the jars of the native modules and runs their tests;
. builds and smoke tests the native executables (Linux amd64 and arm64, macOS arm64 and Windows amd64) from that jar;
. commits the release version (`chore(release): native <version>`), creates and pushes the `native-v<version>` tag;
. creates the GitHub release with the jar, the native executables and their SHA-256 checksums (`SHA256SUMS`), with release notes generated by GitHub (marked as a prerelease if the version has a suffix, e.g., `-rc.1`);
. commits the next development version and pushes it to `main`.

The tag and the commits are only pushed once the jar and all the native executables have been built and tested.
The artifacts are not published to a Maven repository.
The JRuby implementation is released with the *Release* workflow, as before.
